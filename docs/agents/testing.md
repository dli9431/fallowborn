Build, run, and test

There is no game build. The approved development-only Playwright harness lives under tests/e2e/ and may run the real committed index.html in headless Chromium from both file:// and its own local static server. It must not import game scripts as Node modules or introduce runtime dependencies into the game.

From tests/e2e/: npm ci installs the pinned test dependency graph. npx playwright install chromium installs the pinned local browser revision. npm run check runs the fast node --check syntax gate. npm run test:server runs the in-process server, offline-cache, and test-runner support regressions. npm run test:fast reruns preceding Chromium-served failures, or Chromium-served specs affected since that coverage slice's last successful tracked-worktree snapshot. Its successful baseline is reused by test:changed for the Chromium-served slice. npm run test:fast:all runs the full Chromium-served suite without advancing the Chromium-file, Firefox-served, or WebKit-served baseline. npm run test:changed automatically reruns preceding Playwright failures, or runs directly edited/new specs plus the boot and determinism runtime canaries in two slices: Chromium-served from the shared fast baseline, then the other three projects from their matrix baseline. npm run test:all runs the server regression and every configured browser project. npm run test:chromium runs the file and served-origin Chromium suite. npm test is an alias for npm run test:all.

When adding or updating a specification, register its shipped JS, data, and CSS inputs with dependsOnRuntime(__filename, [...]) from support/runtime-dependencies.js. Keep declarations focused; directory-wide declarations are reserved for intentional canaries such as boot and determinism. Import shared journeys directly from the relevant leaf module under support/game/ instead of recreating a common barrel module. These dependency edges are metadata for Playwright's changed-file analyzer only: test:fast uses the full graph, while test:changed bounds it to the whole-runtime canaries and directly changed test code. Never import or execute game scripts in Node. Baseline, line-ending, and helper-authoring details are documented in docs/TESTS.md.

Treat shared test helpers as fan-out boundaries. If behavior belongs to one locale, browser, viewport, or scenario, keep its setup in that specification or a leaf helper imported only by the affected specifications. Do not change support/game/navigation.js, the universal fixture, or the page contract to solve a scenario-local test unless their shared contract truly changed.

These commands are for owner-initiated local runs. AI coding agents must author or update relevant tests, but must not install test browsers or dependencies and must not execute npm run check, Playwright, the static-server regression, runtime verification, profiling, or any other command from the test harness on the local machine. Test execution happens in GitHub Actions instead (see Continuous integration below): agents may trigger those workflows and read their results, summaries, and artifacts. In the final user handoff, report the tests added and state whether and where they ran (for example "not run" or "CI run <id>: passed"). This is handoff-only status; never put it in a commit or merge message. Do not launch ad hoc shell browsers or servers outside this harness. Keep tests deterministic, bounded, and isolated in fresh browser contexts. Manual testing remains required for appearance, touch behavior, itch.io iframe behavior, real mobile browsers, and subjective game feel.

Do not write long multi-year simulation tests. A 20-year 476 campaign test took about 12 minutes and still failed, which proves nothing and blocks the suite. Advance at most one season (90 days) of daily simulation in a test, and only when the daily loop itself is the behavior under test. For annual or long-run rules, stage the dated state directly and call the yearly or boundary hook once or twice. Keep every test well inside the default 60-second timeout, and do not raise test.setTimeout to make a long journey fit. Multi-year stability belongs to targeted boundary tests, the CI season timing, and owner playthroughs, not browser journeys.

Continuous integration

GitHub Actions runs all tests; nothing runs on the owner's machine unless the owner starts it. .github/workflows/tests.yml runs on every push to main, dev, and 476, on pull requests, and by hand: npm run check, npm run test:server, then the changed specs plus the boot and determinism canaries (the test:changed selection) across all four projects, sharded. A manual run can test any pushed branch or commit (target), choose mode=all or mode=specs with an exact specs list, a base commit, projects, shards, and a request_id that names the run. .github/workflows/nightly.yml runs from main every night and by hand: the full suite on 476 and dev, and season timing for every start on 476. .github/workflows/e2e.yml and season-timing.yml are the reusable jobs behind them. docs/TESTS.md, Continuous integration, describes the jobs and artifacts.

Trigger and read runs with the GitHub CLI, for example: gh workflow run tests.yml --ref 476 -f mode=all; gh workflow run tests.yml --ref main -f target=476 -f mode=specs -f specs="specs/boot.spec.js"; gh workflow run nightly.yml -f suite=false -f timing_ref=476; gh run list --workflow tests.yml --branch 476 --limit 5; gh run view <run-id> for job results and the summary; gh run view <run-id> --log-failed for failing step logs; gh run download <run-id> -n report-tests -D ci-report for the merged HTML/JSON report.

Only pushed branches can be tested. To test work, create a new branch and push that; agents never push main or dev. A passing run is evidence, not owner acceptance; visual, device, and play acceptance remain the owner's.

Local load measurements

For owner-controlled startup diagnostics, append ?loadTiming=1 to the local game URL and reload. This records the main menu, bookmark selection and game loading, including Quick Start, Observe and saved games. Each load prints a console report; JSON.stringify(FB.game.loadTiming.reports(), null, 2) returns the latest twenty reports for copying. FB.game.loadTiming.enable(true) enables subsequent loads in the current page, and enable(false) disables them when no load is active. This is local-only, opt-in and transient. Interpret operation selfMs without double counting totalMs, and keep unattributed time distinct from measured synchronous work. The measurement contract is in docs/designs/ui.md. Agents may author coverage in tests/e2e/specs/load-timing.spec.js and inspect owner-provided reports, but must not run measurements or the harness on the local machine.

Local fast-forward profiler

The built-in profiler in js/main.js is disabled by default and available only from file:// or HTTP(S) on localhost, 127.0.0.1, or IPv6 loopback. It is session-only: nothing is stored in saves, preferences, or telemetry.

For an owner-controlled measurement, pause the game and use the browser console:

FB.game.fastForwardTiming.enable(true);

Fast-forward a season using the normal game control, then inspect or copy:

FB.game.fastForwardTiming.last JSON.stringify(FB.game.fastForwardTiming.last, null, 2)

Disable with FB.game.fastForwardTiming.enable(false). Changing the setting during an active fast-forward returns false; enable it before starting the burst. Each completed burst replaces last and prints its report and tables to the console.

Reports include elapsed time, simulated days, batch count, simulation time, time between batches, operation rows, and work counters. Row totalMs includes timed children; selfMs excludes them. Do not add parent and child totals together. maxMs is the slowest individual call, not the whole season. Between-batch time includes browser work; deferred paint and IndexedDB completion are not measured. Save serialization, autosave scheduling, and the final UI refresh have separate rows. Instrumentation itself has overhead.

Army phases and operations cover muster/disband, orders, movement, reinforcement, supply, battles, and sieges/rebellions. Counters expose repeated projections, failed musters, cache hits, source scans, and invalidations. Annual worldTick rows break down population, rulers, succession, religion, diplomacy, and building work. Population rows include capacity/attraction, enterprise upgrade snapshots, migration, settlement changes, and community projects. Annual rows appear only when the burst crosses the year boundary; confirm worldTick.calls is present before comparing annual work with an ordinary season.

Compare the same starting save and season with comparable browser conditions; changing war counts, annual work, or a warmed cache can change the workload. Use counters and self time to identify repeated work before optimizing. Preserve simulation ordering, seeded RNG, and cache invalidation behavior. New timers must remain opt-in and transient, balance enter/leave in finally, and restore wrapped functions after the burst, including errors. Relevant coverage lives in tests/e2e/specs/time-controls.spec.js, annual-world-profiling.spec.js, and army-daily-performance.spec.js. Agents may inspect owner-provided reports and saved traces, and may trigger and read the CI season timing, but must not run profiling or the harness on the local machine.

Season timing

tests/e2e/measure/season-timing.js is a measurement tool, not a regression spec. It enumerates every start the catalogue offers, starts each through the ordinary seed input with automation resolving events, enables this profiler, and fast-forwards season by season. It records wall and simulation time, the slowest rows and counters, and workload (player settlements against their limit, held counties, armies, characters) per season. Its report flags a season far slower than the start's typical season, a season 1.5 times slower than the same season a year earlier, a season 1.5 times slower than the previous nightly measurement, starts that fail or stall, per-day cost that more than doubles, and player deaths, naming the state parts that grew. The nightly profile input (with only) adds a V8 CPU profile per season and lists the top functions by self time with their callers. It runs nightly in CI; the 90-day spec bound does not apply to it.


Paired speed comparisons

.github/workflows/speed-comparison.yml measures an explicit baseline and candidate using one fixed measurement driver. It pins both revisions once, then runs each selected workload on its own hosted machine, alternating baseline/candidate order for 3 to 9 paired samples on that same machine. The default workloads are complete content preparation plus mobile household 476, Peroz 476, Yaghi Siyan 1096 and Muhammad 1204 over four seasons. Each content mode uses a fresh browser context; each simulation sample starts a fresh browser and the same ordinary MEASURE start code. Filesystem and OS caches are not flushed. Alternation reduces order bias but does not remove hosted-machine noise.

Dispatch after the workflow and both game revisions have been pushed: gh workflow run speed-comparison.yml --ref <tooling-ref> -f baseline=<baseline-sha> -f candidate=<candidate-sha> -f repeats=3 -f seasons=4. The subjects input accepts a JSON array of content or bookmark:scenario values. Before the standalone workflow is registered on the default branch, dispatch the same comparison through Nightly on the tooling branch: gh workflow run nightly.yml --ref <tooling-ref> -f suite=false -f timing=false -f timing_ref=<candidate-sha> -f comparison_baseline=<baseline-sha> -f comparison_repeats=3 -f seasons=4. The workflow first runs speed-comparison.spec.js against synthetic measurements to check its calculations and rejection behavior. This does not execute a long simulation as a regression spec.

Each speed-comparison-<job-index> artifact contains comparison.json, summary.txt and all raw pair-N/baseline and pair-N/candidate measurements. JSON records exact game and driver commits, browser version, runner hardware/image metadata, sample order, every measured value, median/min/max, paired percentage gains and the count of faster pairs. Positive gain means the candidate is faster: 100 * (1 - candidate / baseline). Ranges are observed variability, not confidence intervals. Invalid or incomplete workloads fail the comparison; a valid slowdown remains a reported negative gain, not a failed correctness test. Inspect comparison.json subject rather than inferring a workload from the artifact index.

Content preparation checks the expected mod count/signature and refuses already-prepared content. Comparisons reject changed mod signatures. Season comparisons reject absent starts, failures, death, page errors, missing seasons, changed start codes, day counts, dates, RNG/UID or major workload counts. These checks prevent obvious workload mismatches but do not replace deterministic outcome and save compatibility tests. CPU profiling is disabled for speed samples; the existing opt-in season operation timers remain enabled identically on both revisions. Use content-timing.yml or nightly.yml profile=true separately to diagnose hot functions, never mix those profiled times into speed samples. Content preparation and simulation have separate metrics and should not be combined into one speedup.

Season raw workloads retain legacy stateSizes in UTF-16 code units for nightly compatibility and add stateBytes with explicit UTF-8 byte counts for each state part. These are serialized JSON sizes, not compressed save sizes or browser quota consumption. Samples stage no retention history automatically; long-history compaction needs its own staged correctness/size evidence.

A convincing performance claim needs matching workloads, passing correctness coverage, repeated positive gains larger than the observed spread and an appropriate baseline. Record both SHAs and the CI run link. Use more repetitions or independent repeated jobs if gains are noisy; do not declare a target met from a passing spec, one fast run, or reduced work caused by a failed journey.
