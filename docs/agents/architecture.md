Architecture

index.html loads classic (non-module) scripts in a fixed order; everything hangs off two globals. Load order matters  -  do not reorder the <script> tags casually:

Metadata capture exception: js/bookmark_composition.js initializes immediately after data/starts.js, followed by js/bookmark_sources.js and data/bookmark_manifest.js, before the dated builders. They define pure source-order capture and a private native authoring view. Canonical validation/publication requires the complete engine and runs through main.js deferred content preparation after a player requests campaign content. js/util.js preserves this early FB namespace. Do not invoke engine-dependent composition methods from data loading.

The external data and engine tags use defer so fetching does not stop HTML parsing. Execution still follows document order and completes before DOMContentLoaded. Keep defer on newly added bundled scripts, including mods; do not mix async or parser-blocking dependencies into that sequence. Early inline shell scripts must remain independent of the deferred runtime. Initial local load reports include source authoring CPU and resource timing separately. Data files first, all writing to window.FBDATA: data/map_data.js (land polygons, de jure empires/kingdoms/duchies, realms, straits, scripted history, FBDATA.balance), data/counties.js (the ~460-county table, expanding itself into FBDATA.provinces), data/cultures.js, data/technology.js, data/actions.js (the baseline focus/deed metadata projected through private handlers in js/actions.js), data/ambitions.js (regional historical foundations), data/units.js (the unit-class table: composition quality, upkeep, casualty order, counters, and tech/culture gates), data/eras.js (eras: year windows, default government form and culture), data/wardrobes.js (portrait wardrobes that eras and government forms name), data/lexicons.js (political vocabulary and rank ladders by era, government form, faith and culture), data/bookmarks.js (the atomic 867/1066 world definitions), data/settlements.js (the shared physical-site table plus the per-bookmark county settlement layouts it clones onto those bookmark provinces), data/settlements_real.js (generated by tools/settlement_import.py; GeoNames-derived fill: true presentations appended after the curated layouts  -  never hand-edit), data/climate.js (season kinds and climate zones: how each zone maps the global calendar season to a local season kind), data/geographies.js (the geography bases bookmarks name: projection window, grid width, geometry, seeds, map-scale tuning, place names by year, and climate zones), data/traits.js, data/economy.js, data/intrigue.js, the generated data/music_catalog.js, then the event packs (including events_lifepaths.js after events_paths.js, and events_intrigue.js after tournament events and before ruler-agency events). The generated English catalog is absent from an ordinary English boot; a translated boot dynamically loads it before the selected locale. The UI is one system split by file: ui_misc.js loads first and owns the shared internals (FB.ui._shared) that the panel, top bar, feature sheet and lazily loaded ui_modals.js files bind at load. An inert hidden asset pointer keeps ui_modals.js available to deployment stamping and offline precaching without requesting it speculatively. main.js appends the script after the title shell has had a chance to paint and before setting FB.game.bootReady. Preserve that dependency order when changing boot.

js/story_history.js loads after js/stories.js and js/story_campaign.js, before js/stories.js registers data instances from FBDATA.storyInstances. It registers the reusable partition and holy_war factories. Historical declarations stay in the owning bookmark data; restore validates saved records without initializing new people, grants or historical campaign rows.

Historical story type loading

index.html loads data/story_instances.js after bookmark instance sources, including data/story_courts_476.js. js/story_campaign.js, js/story_history.js, js/story_agreements.js, js/royal_settlements.js, js/story_polity_foundation.js, js/story_settlements.js, js/story_courts.js and js/story_track.js load after js/stories.js and before js/main.js. story_track.js depends on story_courts.js. Reusable type files register factories only. At title boot, js/main.js seals factory registration (FB.stories.sealTypes). Unmodded bookmark setup first reviews only its selected date and graphs without sealing instances or capturing the mod baseline. At campaign start or another request for complete content, FB.game.prepareContent restores the pristine authoring baseline, compiles and publishes the bundled FBDATA.storyInstances (FB.stories.load), applies stored mods (FB.mods.applyStored; each mod, including runtime JSON storyInstances, is validated against a detached candidate registry before anything is published), then seals the effective instances (FB.stories.seal) before any world is generated. The compiler places declaration-owned instance batches at their registrationBefore and registrationAfter data anchors, preserving attachment and RNG dispatch order. New type files must declare their source and never select historical content through literal ids. Structural spellings that collide with content ids require explicit protocolFiles reviews and exact per-file counts in the content-id allowlist. Keep protocol literals in their owning files; do not hide them behind shared token tables.

All eleven complete date chains assemble against bookmarkSources.stage's private FBDATA view in their original order, including the dated sources that load on demand (see Per-date bookmark sources). Shared rollouts declare explicit affected dates and isolate each callback with scope. data/bookmark_sources.js seals the manifest after data/bookmark_1066_north_atlantic.js. Unmodded setup and campaign entry review only the selected date, its retained revisions and required shared dependencies. Campaign constructors require FB.game.campaignReady(id) and still recheck the current world and selected start. The lightweight title and date picker use display metadata only. Preserve authored title spellings, surviving predecessor order, typed dependencies, retained revision bindings and later contributors explicitly, following docs/MODDING.md. Per-date bookmark sources

index.html loads the title shell, shared catalogues and the released 867 and 1066 contributors. A few dated files stay eager because shared catalogues depend on them: the five 476 regional catalogues (global legal traditions read by data/intrigue.js, late antique events and cultures), data/bookmark_476_wider_identities.js and data/bookmark_711_identities.js (faith identities named by the globally validated religious institution profiles). Every other dated world, scaffold, story, start and effects file is listed in data/bookmark_manifest.js, which loads immediately after js/bookmark_sources.js and registers through FB.bookmarkSources.manifest. Each run names the eager script the files originally followed, each file names the dates that need it, and each date carries its picker summary (name, desc, date, era, hidden) and the dates it requires. The title and date picker list an unloaded date from that summary. Keep the manifest in index.html order; a new file for a lazy date is added to its run, not to index.html.

FB.bookmarkSources.loadDates(ids, done, progress) injects the missing files of the requested dates and their required dates as script elements with async false, so they execute in manifest order, then replays the sources. Injected URLs inherit the manifest tag's version query unless already stamped; an unstamped file:// document keeps local query-free paths. withBookmarkSetup (date selection and start codes) and prepareCampaignContent (Begin, Observe, Quick Start, Continue and matching save loads) request the selected date. G.prepareContent (any installed mod, the Mods screen, the Chronicle library and authoring) requests every date before complete publication. A file that fails to load withdraws the whole request with a message naming it, keeps the previous catalogue, and stays retryable; complete preparation does not cache that failure. Requests are serialized, and dates already present continue synchronously. prepareSetup and the composition inputs report an unloaded date as not finished loading, and loading is refused once complete content is published.

Every FB.bookmarkSources.stage call is recorded with its document position. Boot runs the eager subset exactly as before, keeps a pristine copy of the authoring root taken at the first contributor, and records the public protected-root changes observed between contributors. A load replays every recorded contributor from that pristine root in document order, with the composition capture streams and native owner fingerprints reset, then seals exactly as boot does. Unprotected roots stay private to the replay; only the difference the newly loaded dates make, measured against a replay of the boot subset, is merged into public FBDATA in source order. Public tables written by ordinary data scripts and inert literal tables are read in place. A date therefore composes as if every script had loaded at boot, and complete content after loading every date equals the former eager catalogue. Contributors must write only through their staged view. Code outside a staged callback in a lazily loaded file runs when the file is injected, before the replay, so it may only declare inert literal tables such as the 634 court tables; work that reads another contributor's output belongs inside the staged callback. Tests that prepend top-level code to such a file serve the former eager document (tests/e2e/fixtures/bookmark-manifest/eager-document.js). An ordinary data script that changes a public protected root must not sit between a lazily loaded run and the next eager contributor; the boot pass records a manifest fault for that ambiguity. Keep the private debug loader aligned with the manifest as well as index.html.
