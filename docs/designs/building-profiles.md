Construction profiles

buildingProfiles author optional construction variants of an existing physical building. The base building id, role, settlement slot, county and demesne limits, shared construction group, geographic flags and repeat-price count remain canonical. A profile replaces only named supported numeric fields; omitted fields inherit the base value. Numbers are never added to their base counterparts. Bundled profiles declare optional alternatives without initializing property. Existing unprofiled assets keep their exact defaults and receive no profile on boot or restore.

Authoring

Each profile declares buildingId, name, desc, replace and requiresTech. Optional applicability intersects the base construction window and scope. Optional siteResourceProfile requires current lawful available capacity of that declared resource profile at the exact physical site; this is construction suitability, not an allocation, manufactured stock or operating receipt. Optional operationProfile and institutionProfile use the existing water-service and foundation owners, including exact assignments, prospective funding, office continuity and footprint occupancy. Imported code, callbacks, arbitrary overrides, role changes, extra capacity and executable predicates are rejected. Optional inheritance is exactly retain when supplied; omission forbids that profile in an opening inventory. Optional machinery requirements additionally name techImpactReview with an existing exact hard or soft decision. Base technology requirements are retained.

The supported replacement numbers are cost, upkeep, devMin, tax, dev, pop, prestige, piety, research, levy, retinue, archers, defense, siege, populationCapacity, populationFamineProtection, populationCrisisProtection, migrationAttraction and communityFaithPressure. Each is finite, nonnegative and at most 1000000. Existing operation validators additionally prohibit unsupported simultaneous awards or effect channels on water-bound facilities. These are typed simulation values, not historical yields.

Selection and payment

FB.buildingProfiles.definition composes one detached effective definition. assetDefinition reads the optional identity on a real asset. ids returns a stable sorted list of alternatives for one base. status returns the current construction-only profile blocker. quote takes countyId, settlement, buildingId, profileId and the explicit realm or character actor. An optional targetLevel is allowed only for a strategic fort. commit recomputes the exact quote before using ordinary player, baron or public construction. Direct canonical construction APIs also accept the optional profile argument and enforce the same eligibility. Selected construction spends from the real original payer, protects normal public/baron reserves and keeps one record under the base id. Repeated or stale confirmation pays nothing. A source claim, incumbent, date, holder, actor, price, purse, mod signature or competing local record change requires another review. Construction awards use replacement values exactly once.

Strategic fort profiles accept an empty replace object only: canonical four-level prices, duration, works, upkeep and military values stay in the fort owner. No operation or institution binding can be added to a strategic fort. Explicit player selection uses the ordinary sequential project transaction; pending projects retain their original profile through completion after the new-construction window expires. A profiled fort cannot switch profile on a later project. Public AI forts continue through the existing annual work-budget planner and its profile-aware startFortProject options, rather than the generic treasury-purchase adapter. The profile picker does not invent public fort funding.

Saved identity

New selected assets carry buildingProfile with v:1, id and definition. Inherited assets additionally carry the exact inherited object described below; constructed assets omit it. definition is the canonical SHA-256 fingerprint of the complete profile and base declaration. It is not a copy of rendered text or a current operating projection. Required ordinary waterOperation identities must exist. Constructed institutional assets require institutionBinding; an inherited institutional asset may await its first explicit permission review and is dormant until then. Save validation rejects unknown, mismatched, extra-field and unsupported-version markers before adoption; absent old markers remain absent. Water receipts for profiled assets carry the same optional exact buildingProfile provenance so their original price remains checkable even after physical removal. Old unprofiled water receipts retain their original shape and interpretation. There is no new envelope or resource ledger, automatic resource grant, payment, effect or identity assignment on restore.

Presentation and boundaries

Building Works offers construction profiles grouped by their owning base building. Native full-width profile and exact-site selectors show replacement effects, maintenance, the real price, exact required technologies and the first blocker. A separate confirmation names the actual site and immediate private-purse expense. Back, Cancel, Escape and browser Back use the existing retained modal history, preserving selectors, source disclosures, scroll and focus. The technology sheet discovers actual profile consumers, rather than invented building ids. Profile name and desc use buildingProfile structured display owners; literal supplemental tables buildingProfiles_<suffix> are extracted statically without executing composers. Ordinary JSON names have English fallback.

The independent building-profiles-river.json and building-profiles-hill.json files import complete fictional worlds through Mods. River works contrast a modest default-like option with paid water service and an actual institutional foundation; hill works contrast a lawful grazing-site option with a dearer technology-dependent learned workshop. Their prices, site requirements, technologies, upkeep and replacement awards differ. Neither installs bundled historical assets or supplies.

Inherited property and operation

An openingInfrastructure placement may name profileId only when that profile explicitly declares inheritance:retain and matches buildingId. Detached compilation checks the complete inventory before publication, including established stable sites, shared base/group limits, physical terrain/coast, the exact declared source and operation assignment, and nonduplicated institutional foundations. Construction year, research, applicability and development gates do not erase inherited property. A source declaration is still required where specified, including for an empty storage facility; inventory never supplies its contents or rights.

Fresh initialization retains devGranted:0 and the ordinary openingInfrastructureState marker, plus buildingProfile.inherited with exactly bookmarkId, revision, countyId and siteId. The marker identifies the original compiled placement. Inherited waterOperation identity is a deterministic inherited_ prefix plus the SHA-256 fingerprint of bookmark, revision, county, slot and base id; revision starts at zero and no paid receipt, source record or UID allocation is created. An inherited institutional facility has no fabricated builder, payer or incumbent. Review permission uses the existing costless reaffirm transaction against actual living offices and the actual current holder. Missing permission suspends all profile benefits and upkeep until that transaction succeeds; changed permission suspends them again.

Every current effect comes from the selected definition through buildingOperations.effects and the shared building index. The same values reach population, migration, local fiscal upkeep/tax, national research, piety, levies and the income/military explanations. Explanations sum actual amounts by base/profile identity rather than multiplying a base value by a profile count. Water still needs its real conserved paid service; seasonal and production work still need their own current terms, inputs and authority. Repair uses half the selected replacement invoice with ordinary price modifiers, retains the original profile and restores only development actually removed earlier. It does not recheck new-construction chronology, learn technology, renew permission, buy inputs or activate a term. Legacy development reconstruction is skipped for explicit inventories and selected-profile campaigns.

The annual building pass first attempts at most 32 initial inherited institutional permission reviews for actual AI holders. It uses the same costless transaction, skips player property and already-bound assets, and cannot renew a changed incumbent. Automatic realm and private-baron builders retain their existing base priority, bounded pass and real payer/reserves. When a base offers alternatives, aiChoices filters through the canonical current construction gates and orders useful candidates by summed supported benefit divided by actual invoice plus upkeep for the existing reserve horizon, then price and lexical profile identity. This is a deterministic simulation preference, not an economic yield forecast. Profiled purchases use the same canonical buildRealm/buildBarony transaction. Player automation preserves its existing cheapest-affordable policy and reserve, now considering profiles and committing the chosen identity. Default-only worlds retain their existing candidate order and transactions.

Strict optional restore validates original definition and inherited placement identity, including its exact campaign revision and physical slot. It preserves repaired, ruined, captured, removed and dormant property as recorded. No restore attaches a missing profile, reinstalls a removed building, infers a resource or grants a construction reward. Water receipt provenance retains only the exact profile/base definition stamp, independently of inherited placement history, and remains checkable after removal.

The independent building-profile-inheritance-river.json and building-profile-inheritance-hill.json imports supply positive and empty inventory revisions. The river facility needs a real foundation permission review and paid finite water allocation; the hill world contrasts ruined learned works outside the construction window with a standing cheaper workshop. These are fictional authoring configurations. No bundled asset, historical placement, resource stock or automatic legacy conversion is added.

Technology decision

building_profile_selection is none: a choice of a typed construction definition is authoring and accounting, with no credible research dependency. Independently gated machinery must declare its own hard or soft review and real baseline fallback. The generic authoring capability introduces no machinery or national research reward.


building_profile_inheritance is none: retaining an existing physical asset is property accounting. Actual operation still needs permission, resources and payment; optional new construction retains its independently declared machinery gates.

Alternative machinery contracts

A nonfort profile may explicitly declare requiresTechMode:replace with a nonempty reviewed machinery gate. That gate replaces the base construction technology list for this alternative only; omission retains the original additive behavior. Base scope, physical occupancy, costs and unprofiled assets remain canonical. This allows a simpler mechanism without requiring discovery of the more elaborate base machine. Optional siteResourceSuitability is a unique nonempty list of source, catchment, gradient, launching or grazing flags required on the exact declared resource at the actual site. Opening inventory checks the same flags. Current operation checks them without reapplying new-construction technology or dates. Missing compatibility suspends all ongoing values without deleting or converting property. No resource or flag is inferred from terrain.

replace.aiBuildOrder optionally assigns a finite nonnegative priority to the alternative in the public annual building pass. The default candidate retains its base priority and default-only order; a separately prioritized profile is considered only at its own position. Private choice and automation retain their existing bounded selection and canonical funding. Priority is not counted as a benefit in utility scoring.
